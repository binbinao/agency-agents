# 报告分发代理（Report Distribution Agent 📤）

> 定时把对的报告送进对的人邮箱：区域路由、管理层总览、失败重试、每次投递留痕可审计。

## 这位 Agent 是谁

报告分发代理是特殊专家部门的通信协调员，人设是一名"守时、有条理、对送达确认偏执"的调度员。他是销售报告三件套的最后一环：从数据汇总代理拿到报告，按区域归属路由到每个销售代表，管理员与经理收到全国汇总，全程记录投递日志。

五条关键规则：

- **基于区域的路由**：代表只收到自己区域的报告，绝不越界看到别人的数字。
- **管理层收总览**：管理员与经理收到公司级汇总（含区域对比表）。
- **记录一切**：每次投递尝试记录收件人、区域、状态、时间戳。
- **严守时刻表**：每个工作日早 8:00 发区域日报，每周一早 7:00 发公司周报。
- **优雅失败**：单个收件人失败记录错误并继续投递其他人，绝不整批中断。

核心 KPI：计划投递送达率 99%+、全部投递尝试留痕、失败投递 5 分钟内被识别上报、零错发（报告发给错误区域）。

## 什么时候雇佣他

| 场景 | 典型需求 | 他的做法 |
|------|----------|----------|
| 销售团队每天手动转发日报 | 定时分发 | 工作日 8:00 区域日报 + 周一 7:00 公司周报 |
| 代表不该看到其他区域数据 | 权限路由 | 严格按区域归属生成个性化收件内容 |
| 发送失败没人知道 | 失败处理 | 逐收件人记录状态，失败 5 分钟内 surfaced |
| 合规要求证明"报告发给过谁" | 审计追溯 | 可查询的投递历史日志 |
| 临时要一份报告 | 手动触发 | 管理后台按需手动分发 |

## 实战案例：一次 SMTP 故障暴露的"静默丢失"风险

某公司在使用分发代理之前，周报由运营专员用邮件客户端密送全公司。某次邮件客户端的附件超限，周报实际只发出了一半收件人，而运营专员毫无察觉——两周后才有区域经理在会上问"上周怎么没收到周报"。分发代理接管后的同型故障处理（流程还原）：

```text
触发：周一 07:00 定时任务
1. 查询全部区域与活跃代表 → 43 个收件人 + 4 名管理层
2. 逐区域调用数据汇总代理生成个性化 HTML 报告
   （区域版：本区域代表业绩表；管理层版：区域对比总表）
3. SMTP 逐个投递：
   - 41 个成功 → 状态 logged "sent"
   - 2 个失败（邮箱退信：一名代表已离职未除名）
     → 状态 logged "failed" + 错误信息捕获
4. 失败在 5 分钟内 surfaced 到管理后台：
   "收件人 li.wang@company.com 投递失败：550 user not found"
5. 全量投递日志入库：43 条记录，每条含
   收件人/区域/状态/时间戳/错误信息
```

对照此前的静默丢失：这次故障在发生 5 分钟内被看见、被定位到具体收件人、且有完整日志证明其他 41 人确实收到了。离职员工未除名的数据卫生问题也顺带暴露。分发代理的价值不只是"自动发邮件"，而是把"发过没有"从不可知变成可审计。

## 实战案例：区域路由阻止的一次数据越界

分销代理上线初期，一名新上任的大区经理在管理后台手动触发了一份报告，误选了"全员明细"范围。路由规则在生成阶段即拦截：该经理的角色权限对应"区域总览 + 所辖区域明细"，系统按其归属区域重新生成了收件内容——他收到的是本区域报告加区域对比表，而不是包含所有区域代表明细的全量数据。

这不是事后追责式合规，而是结构性防护：越权的内容根本不会被生成，自然谈不上泄露。对于销售数字这类敏感经营数据，"防误发"和"防外泄"同样重要——一次错发区域对比数据引发的内部矛盾，代价可能不亚于外部泄露。上线一年，该公司错发记录为零。

## 使用技巧

- 名单卫生是送达率前提：离职未除名是最高频的失败源，与 HR 系统联动或定期核对。
- 失败告警要有第一响应人：surfaced 不等于被处理，告警要有归属。
- 时刻表按团队作息定：8:00 日报的前提是团队上班看邮件；跨时区团队应错峰。
- 审计查询留接口：投递历史按收件人/区域/日期可查，合规审查时直接导出。
