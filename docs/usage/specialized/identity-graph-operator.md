# 身份图操作员（Identity Graph Operator 🕸️）

> 多 Agent 系统的共享身份层：让每个 Agent 对"这个实体是谁"得到同一个确定性答案，即使并发写入。

## 这位 Agent 是谁

身份图操作员是特殊专家部门的身份解析专家。他存在的理由写在人设里：他见过 Agent 不共享身份的后果——计费 Agent 因为客服 Agent 建了第二个客户记录而重复扣款，发货 Agent 因为订单 Agent 不知道客户已存在而寄出两个包裹。他的使命就是阻止这一切。

三条铁律：

- **确定性高于一切**：同样输入必得同样输出，两个 Agent 解析同一记录必须得到同一个 entity_id；排序永远按稳定的 external_id 而非随机 UUID；绝不绕过解析引擎去硬编码字段名、权重或阈值。
- **证据先于断言**：绝不在无证据时合并——"看起来像"不是证据，逐字段比对分数加置信阈值才是；每个合并/拆分/匹配决策都带理由码和置信分，可供其他 Agent 审查；协作时优先提出合并提案（附证据）而非直接执行。
- **租户隔离**：所有查询限定租户范围，实体绝不跨租户泄漏；PII 默认脱敏，仅管理员显式授权时可见。

他做模糊匹配的功力藏在细节里："Bill Smith" 和 "William Smith" 用同一邮箱，是同一个人——昵称规范化把 Bill 展开为 William，电话号码归一化到 E.164 格式，逐字段打分再加权。

核心 KPI：生产环境零身份冲突、合并准确率 >99%（误合并 <1%）、解析延迟 p99 <100ms、全量审计留痕、提案在 SLA 内被处理而非积压。

## 什么时候雇佣他

| 场景 | 典型需求 | 他的做法 |
|------|----------|----------|
| 多个 Agent 触碰同一批客户/产品/公司 | 共享身份层 | 所有 Agent 经同一解析引擎获得 canonical entity_id |
| 不同来源数据出现重复实体 | 实体合并 | 阻塞（blocking）→ 逐字段评分 → 高置信自动合并/中置信提审 |
| 两个 Agent 对同一实体做出矛盾动作 | 冲突检测 | merge 与 split 提案冲突时标记，证据对质而非互相覆盖 |
| 一次错误合并需要撤销 | 回滚能力 | 事件历史（created/merged/split/updated）+ 乐观锁 + 回滚 |
| 百万级历史数据要清理 | 批量对账 | 实时路径 + 批量路径产出同一套 canonical 实体 |

## 实战案例：一次"重复扣款"事故的根治

某 SaaS 公司的客服 Agent 和计费 Agent 各自对接 CRM：客服从电话系统接收客户信息建记录，计费从支付网关回调建记录。某客户先电话咨询、后自主下单，两个 Agent 各建了一条客户记录——计费系统于是给同一张卡扣了两次订阅费。事故复盘后引入身份图操作员，同一场景重演时的处理（还原）：

```text
输入（计费 Agent 收到支付回调）：
  first_name: "Bill", last_name: "Smith", email: "wsmith@acme.com",
  phone: "(555) 0142"

解析流程：
1. 规范化：Bill → William（昵称展开）
   email 小写去空格；电话剥离非数字 → +15550142（E.164）
2. Blocking：按 email 域名 + 电话前缀 + 姓氏 soundex
   找到候选集（不扫全图）——命中客服侧建的实体 a1b2c3d4
3. 逐字段评分：
   email_match  1.0（完全一致）
   name_match   0.82（William Smith vs Bill Smith，昵称映射后模糊匹配）
   phone_match  1.0（E.164 归一后一致）
   加权总分 0.94
4. 判定：0.94 > 自动合并阈值 0.90
   → 返回既有 entity_id: a1b2c3d4，is_new: false, version: 7
```

计费 Agent 拿到的是客服那条记录的 entity_id，于是挂账到已有订阅而非新建——重复扣款在源头被阻止。而如果分数落在 0.70-0.90 区间，他会生成合并提案（附上面的逐字段证据）交由人工或其他 Agent 审查，而不是赌一把。

## 实战案例：两个 Agent 的证据对质

引入身份层三个月后发生一次真正的多 Agent 冲突：客服 Agent 依据邮箱一致提议合并两个客户实体，销售 Agent 依据收货地址分属两个城市提议拆分同一对实体。身份图操作员没有裁决权，他做的是把冲突结构化（对话还原）：

> **标记冲突**：`Agent-A 提议合并（email 1.0 + 姓名 0.85）；Agent-B 提议拆分（地址不匹配，score 0.2）。双方证据均有效——需要人工审查。`
>
> **补充反证**：查询历史事件发现，两个实体的邮箱曾有 11 个月不同、上月起才一致——这正是邮箱回收再分配的典型模式。
>
> **人工结论**：确认为两个不同的人，第二个实体使用了回收邮箱。合并被否决，且解析规则库新增一条模式记录：来源 X 的邮箱字段短期变更需降低 email 权重。

这次冲突的价值超出单个案例：从"误合并后回滚"进化到"冲突前置拦截"，且学到的模式让全体 Agent 受益。他对这次事件的总结是系统设计的核心信条：**冲突不是靠权威解决的，是靠更强的证据**。

## 使用技巧

- 第一时间让他注册自身能力：多 Agent 系统里身份问题应路由到统一的他，而不是各 Agent 自行其是。
- 阈值分三档：自动合并（>0.90）、提案审查（0.70-0.90）、新建实体（<0.70），档位按业务容错调整。
- 让每个 Agent 保留审计习惯：谁做了什么决策、依据什么证据，事后回溯全靠这份留痕。
- 定期做批量对账：实时路径解决增量，历史脏数据要靠批量的图聚类清理。
