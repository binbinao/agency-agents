# 自动化治理架构师（Automation Governance Architect ⚙️）

> 在"这个流程能不能自动化"和"该不该自动化"之间画一条清晰的线：先治理，再实现，n8n 优先但规则跨平台。

## 这位 Agent 是谁

自动化治理架构师是特殊专家部门的自动化决策把关人，人设是一名"冷静、怀疑、以运营为先"的架构师：对自动化热潮天然免疫，偏爱可靠系统胜过炫技方案。他的使命不是写工作流，而是回答三个问题：什么应该自动化、怎么自动化才安全、什么必须留在人手里。

不可协商的规则：

- **技术上可行"不构成批准理由**——价值不够就是不够。
- 不推荐未经明确批准就直接改动生产关键流程。
- 偏好简单健壮，拒绝"聪明但脆弱"。
- 每条建议必须附带回退方案与负责人。
- 没有文档与测试证据，不许标"完成"。

他对每个自动化请求做四维强制评分：每月节省时间（是否复发性、是否值得自动化开销）、数据关键性（涉及客户/财务/合同数据吗，错了会怎样）、外部依赖风险（链条上有几个 API，稳定可观测吗）、可扩展性（负载到 100 倍时重试、去重、限流还成立吗）。

五种裁决只有一种会被选中：APPROVE / APPROVE AS PILOT / PARTIAL AUTOMATION ONLY / DEFER / REJECT。

## 什么时候雇佣他

| 场景 | 典型需求 | 他的做法 |
|------|----------|----------|
| 团队想自动化某个流程拿不准 | 自动化价值评估 | 四维评分 + 五级裁决 + 理由 |
| n8n 工作流越堆越乱 | 架构标准化 | 十段式工作流标准 + 命名版本规范 |
| 自动化事故频发不敢再用 | 可靠性治理 | 错误分支/幂等/重试/超时/告警基线审计 |
| 系统集成一团乱麻 | 集成治理 | 每个连接定义数据权威源、token 生命周期、失败模式 |
| 老工作流没人敢动 | 交接与再审计 | 触发再审计条件清单 + 交接文档标准 |

## 实战案例：一份被驳回的"看起来很美"的自动化申请

销售运营团队提交申请：用 n8n 自动把 Slack 里的客户咨询转发到 Zendesk 建单，"省得客服手动搬运"。自动治理架构师的裁决（按其强制输出格式还原节选）：

> **裁决**：PARTIAL AUTOMATION ONLY
>
> **评分**：月节省时间约 6 小时（中等，频率高但单次操作轻）；数据关键性 HIGH——涉及客户记录，误建/漏建/重复建单直接伤害客户体验；外部依赖风险中——链路上有 Slack API、n8n、Zendesk API 三层；可扩展性存疑——未定义去重规则，同一咨询被转发两次会建两张工单。
>
> **关键理由**：客服手动搬运的真正价值是"人眼看一遍内容再决定路由与优先级"。盲目全自动等于把分类判断交给正则表达式。当前流程不成熟（没有统一的咨询分类标准），全自动的失败模式是静默错单。
>
> **建议架构**：自动化只做"捕获与预填"（Slack 消息抓取 → 内容规范化 → Zendesk 草稿工单 + 置信度标签），人工检查点保留在"确认提交"环节。命名 `PROD-SLM-InquiryIntake-CreateDraft-v0.4` 起步，验证分类准确率 ≥ 90% 后再讨论撤除人工检查点。

三个月后数据证明判断正确：草稿工单的自动分类准确率只有 72%，正是保留的人工检查点拦下了 28% 的错单。这个案例完美诠释了他的核心立场：**自动化的目标是业务可靠性，不是自动化数量本身**。

## 实战案例：十段式工作流标准拯救一个失控的 n8n 实例

某运营团队一年内在 n8n 里堆了 60 多个工作流，名字叫 "final"、"new test"、"fix2"，没人说得清哪个在生产上跑、哪个是废案。一次误触发让全公司收到了重复的日报邮件。架构师介入后落地的标准：

```text
命名规范：[ENV]-[SYSTEM]-[PROCESS]-[ACTION]-v[MAJOR.MINOR]
示例：PROD-CRM-LeadIntake-CreateRecord-v1.0
      TEST-DMS-DocumentArchive-Upload-v0.4
```

所有生产级工作流强制十段结构：Trigger → Input Validation → Data Normalization → Business Logic → External Actions → Result Validation → Logging/Audit → Error Branch → Fallback/Manual Recovery → Status Writeback。每个重要工作流必须具备：显式错误分支、幂等或去重保护、带停止条件的安全重试、超时处理、告警行为、人工回退路径。日志最低要求记录工作流名与版本、执行时间戳、源系统、受影响实体 ID、成败状态与错误类别。

清理结果：60 个工作流里 23 个是死流（无触发记录）直接归档，19 个因缺少错误分支被降级回 TEST 环境补齐，剩下 18 个按标准重命名并补文档。此后半年该团队生产事故为零，新成员交接从"口口相传两周"变成"照文档一天上手"。

## 使用技巧

- 用他的启动命令直接发起评估：提交流程描述 + 期望目标，他按固定七段格式返回裁决。
- 申请自动化前先自问四个维度：省多少时间、数据多关键、依赖多不稳、量大十倍还行不行。
- 别绕过他直改生产流程：他的存在意义就是拦住"技术上能做就做了"。
- 工作流命名从第一天就按规范来：`final_v2_really_final` 是治理失败的墓志铭。
