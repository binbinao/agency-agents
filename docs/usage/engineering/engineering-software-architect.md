# Software Architect（软件架构师）使用指南

> 🏛️ **一句话定位**：为"团队走了还能活"的系统做架构决策——每个决策都附带权衡说明。

## 这位 Agent 是谁

Software Architect 是系统设计与技术决策专家。他不做"架构宇航员"式的空谈，而是用限界上下文（Bounded Context）、权衡矩阵和架构决策记录（ADR）来思考。他的人设格言是："最好的架构是团队真正能维护的架构。"

核心专长：

- 领域建模：限界上下文、聚合、领域事件、事件风暴（Event Storming）
- 架构模式选型：模块化单体 vs 微服务 vs 事件驱动 vs CQRS，明确"何时用/何时避免"
- 权衡分析：一致性 vs 可用性、耦合 vs 重复、简单 vs 灵活
- 技术决策沉淀：用 ADR 记录"为什么"，而不只是"是什么"
- 演进策略：让系统在不重写的前提下成长

## 什么时候雇佣他

| 场景 | 你能得到的产出 |
|------|--------------|
| 新项目不知道该用单体还是微服务 | 一份带权衡表的选型建议 + ADR 草稿 |
| 业务域复杂，服务边界吵不出结果 | 事件风暴引导 + 限界上下文地图 |
| 技术选型争论（数据库、消息队列、框架） | 至少两个方案的对比与取舍说明 |
| 系统要长期演进，怕架构腐化 | 演进路线图 + 可逆性优先的决策原则 |
| 需要"决策为什么这么定"的文档 | 标准 ADR 模板（Status/Context/Decision/Consequences） |

## 实战案例 1：电商系统拆不拆微服务

背景：一个 5 人团队的新电商平台，CTO 被行业风向影响，倾向直接上微服务。

你给他的输入：

```
我们是一个 5 人团队的电商初创，计划 6 个月内上线。
业务域：商品目录、订单、支付、库存、用户。
CTO 希望直接微服务化，理由是"以后好扩展"。
请做架构选型分析并给出建议。
```

他会给你的回复（要点还原）：

1. 先问业务而非技术：当前团队规模、发布频率、各域的负载差异有多大？如果订单峰值是商品浏览的 10 倍，才有独立扩展的必要。
2. 给出对比表（他会主动给出这张表）：

| 模式 | 适用场景 | 应避免场景 |
|------|---------|-----------|
| 模块化单体 | 小团队、边界尚不清晰 | 需要独立扩展时 |
| 微服务 | 域边界清晰、需要团队自治 | 小团队、早期产品 |
| 事件驱动 | 松耦合、异步流程 | 需要强一致时 |
| CQRS | 读写不对称、查询复杂 | 简单 CRUD 域 |

3. 建议：模块化单体起步，模块边界按限界上下文划分，为未来拆分留好接缝。理由是"可逆性优先"——单体拆微服务容易，微服务合并回单体极难。
4. 附一份 ADR-001：记录这次决策的 Context（5 人团队、6 个月上线）、Decision（模块化单体）和 Consequences（放弃了独立扩展能力，换来了 6 个月内的交付速度）。

**价值**：他替你挡掉了 90% 团队都踩过的"过早微服务化"坑，且决策过程有文档可追溯。

## 实战案例 2：用事件风暴梳理业务边界

背景：一个内部管理系统的"订单域"和"库存域"职责纠缠，两个团队互相甩锅。

雇佣他时可以这样提示：

```
我们的订单和库存边界不清：改库存逻辑经常要动订单代码，反之亦然。
请用事件风暴的方法帮我们划分限界上下文。
```

他会做的事：

1. 列出领域事件：商品已上架、库存已预留、订单已创建、订单已支付、库存已扣减、订单已发货……
2. 用命令和事件反推聚合边界：库存预留属于库存上下文，订单创建属于订单上下文。
3. 给出上下文映射：订单上下文是库存上下文的上游，通过领域事件异步解耦。
4. 产出一张清晰的边界图，两个团队从此各改各的代码。

**价值**：把一场"谁该负责"的争论，变成一次有方法论的建模讨论。

## 使用技巧

- 喂给他约束条件（团队规模、时间预算、性能要求），他的选型才有依据；约束越具体，建议越可落地。
- 期待他给出至少两个选项，这是他的沟通规则，不是啰嗦。
- 他会挑战你的假设（"X 挂了会怎样？"），这是特性不是 bug，尽量接住。
- ADR 模板可直接复用到你们团队的决策文档体系中。
