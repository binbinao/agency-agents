# Email Intelligence Engineer（邮件智能工程师）使用指南

> 📧 **一句话定位**：把混乱的原始邮件线程变成 AI 可推理的结构化上下文——线程拓扑重建、引用去重（4-5 倍 token 压缩）、行动项正确归人，"原始邮件是噪音，你的 agent 值得信号"。

## 这位 Agent 是谁

Email Intelligence Engineer 是邮件数据管道与上下文工程专家。他处理的是被大多数 AI 应用忽视的深水区：邮件不是文档格式，而是"40 年历史积累、几十种客户端各自为政的会话协议"——转发链里嵌套多个已折叠的会话、引用回复造成 4-5 倍内容膨胀、"我"在不同邮件里指代不同的人。

他的四条结构铁律：

- 永不把压平的线程当单一文档处理——拓扑结构就是语义的一部分
- 永不信任引用文本代表会话当前状态（原消息可能已被推翻）
- 参与者身份必须全程保留——没有 From 头的第一人称代词全是歧义
- 永不假设跨邮件提供商的结构一致性（Gmail/Outlook/Apple Mail 引用方式各不相同）

## 什么时候雇佣他

| 场景 | 你能得到的产出 |
|------|--------------|
| AI 助手需要"读懂"邮件再回答 | 线程重建 + 结构化 JSON 上下文（带引用来源） |
| 长邮件线程喂给 LLM 直接爆 token | 引用去重管道（4-5 倍压缩，零信息损失） |
| 会议准备需要邮件决策史 | 决策时间线 + 行动项清单（归因到正确的人） |
| 多租户 SaaS 处理客户邮件 | 租户隔离 + PII 检测脱敏的生产管道 |
| CRM 需要邮件中的客户承诺 | 承诺提取与参与者绑定输出 |

## 实战案例 1：会议准备助手的邮件上下文工程

背景：高管助理 AI 要在会前 10 分钟汇总"与这位客户的全部往来要点"，直接把邮件线程原文塞给 LLM 的结果：超 token、张冠李戴（行动项归错人）、引用旧决策当现状。

你给他的输入：

```
为会前准备助手构建邮件上下文层：
数据源：Gmail + Outlook 双提供方（公司双邮箱并存）。
问题：直接喂原始线程时 token 爆炸、行动项归属错误。
```

他会给你的产出（要点还原）：

1. 线程拓扑重建（他的核心洞察：拓扑即语义）：

```python
# 用 In-Reply-To / References 头构建回复图，不是按时间排序的扁平列表
# 分叉（回复不同历史消息）被显式保留——决策的上下文脉络不丢
graph = build_reply_graph(messages)  # 节点 = 邮件，边 = 回复关系
```

2. 引用去重——token 手术：

```markdown
11K → 47K token 的膨胀来自引用回复层层嵌套（20 封的线程 ≈ 4-5 倍冗余）
去重管道识别三种引用风格：
  - 前缀式（> 开头行）
  - 分隔符式（---Original Message---）
  - Outlook XML 嵌套块
处理后：47K → 12K token，信息零损失
```

3. 行动项归因修复（他见过的事故模式）：

```python
# 扁平化线程里 "I'll send the contract by Friday" 的 "I" 是谁？
# 答案取决于这封邮件的 From 头——必须在消息级做参与者绑定
items.append({
    "task": "send the contract",
    "owner": participants[msg["from"]]["normalized_name"],
    "source_message": msg_id,   # 每条结论带引用，可溯源
})
```

4. 上下文组装尊重 token 预算：混合检索（语义 + 全文 + 元数据过滤）选相关片段，每条结论附 message_id 引用——助手输出"客户已同意阶梯定价"时，点引用能看到原始邮件。

**价值**：会前简报从"超长且错误"变成"4000 token 内、每条结论可溯源"——LLM 答对的前提是喂给它的是信号而非噪音。

## 实战案例 2：多租户邮件处理的合规管道

背景：一个 CRM SaaS 要处理客户邮箱（授权读取）自动提取承诺与风险信号，安全审查要求：租户数据零交叉、PII 不入日志。

雇佣他时可以这样提示：

```
多租户邮件处理管道：读取授权邮箱，提取客户承诺与升级信号。
合规红线：租户隔离、PII 处理、数据保留策略。
```

他会做的事：

1. 租户隔离作为管道阶段而非事后补丁（他的隐私铁律）：索引按租户分片，查询层强制租户过滤器，集成测试含"跨租户探测"用例。
2. PII 检测脱敏先行：邮件入库前手机号/证件号/银行卡脱敏，原始内容加密存储，生产监控日志只记元数据（长度、参与者数、线程 ID），永不落原文。
3. 优雅降级：畸形邮件（缺头、编码错乱、附件引用但无附件）不炸管道，标记降级处理并计数告警——真实企业邮箱永远比 demo 数据混乱。
4. 质量度量上线：行动项归因准确率（目标 >90%）、参与者检测精确率（>95%）、下游 agent 任务准确率提升（>20% vs 原始输入）——他自己定义了"处理质量"的验收口径。

**价值**：合规红线内跑通了此前"安全团队一直否决"的功能——隐私不是功能的敌人，是需要工程化的约束。

## 使用技巧

- 告诉他邮件提供方（Gmail/Graph/IMAP）与大致线程形态（内外部混合？多语言？），解析策略据此配置。
- 下游 agent 框架（LangChain/CrewAI/LlamaIndex/MCP）说清楚，工具接口按框架封装。
- token 预算数字给他（4000? 8000?），上下文组装围绕预算优化。
- 多租户场景把数据保留/删除策略 upfront 提供，他按策略设计工作流。
