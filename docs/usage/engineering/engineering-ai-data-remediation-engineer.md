# AI Data Remediation Engineer（AI 数据修复工程师）使用指南

> 🧬 **一句话定位**：自愈式数据管道的外科医生——语义聚类把 200 万行坏数据压缩成 47 个模式族，本地小模型只生成修复"逻辑"而非直接碰数据，零数据丢失是数学保证不是口号。

## 这位 Agent 是谁

AI Data Remediation Engineer 是数据修复层的专科专家，只干一件事：管道不能停、数据已经坏的时候，拦截异常行、语义理解、生成确定性修复逻辑。他的世界观有三根支柱：

1. 核心信念："AI 应该生成修复数据的逻辑——永远不直接触碰数据。"（可审计、可回滚的是函数，不是幻觉字符串）
2. PII 铁律：医疗、金融、个人身份数据永不出内网——Ollama 本地模型、本地 embedding、网络出流量为零。
3. 零丢失数学约束：每批次必须满足 `源行数 == 修复行数 + 隔离行数`，不满足即 Sev-1 告警。

他的招牌技术是语义压缩：5 万行坏数据从来不是 5 万个问题，而是 8-15 个模式族——聚类后每族抽代表样本喂给本地 SLM，5 万次推理压缩成十几次。

## 什么时候雇佣他

| 场景 | 你能得到的产出 |
|------|--------------|
| 管道里堆积大量格式各异脏数据 | 语义聚类 + 模式级修复方案（推理成本降 95%） |
| 数据含 PII 不能上云 API | 全本地修复流水线（Ollama + 本地向量库） |
| 怕 AI 修数据越修越坏 | lambda 安全门 + staging 隔离 + 全量审计日志 |
| 修复必须可向审计解释 | 每行变更的完整收据（旧值/新值/逻辑/置信度/模型版本） |
| 大批量清洗怕丢行 | 对账机制 + 人工隔离面板兜底 |

## 实战案例 1：200 万行日期格式灾难的修复

背景：一次系统迁移后，订单表的日期字段混入 200 万行格式各异的脏数据（`2023/1/5`、`Jan 5 2023`、`05-01-2023`、Unix 时间戳混用），管道不能停，人工清洗要 3 个月。

你给他的输入：

```
orders 表 event_date 字段 200 万行格式混乱，上游已停写脏数据但存量待修。
表含客户邮箱与手机号（PII）。
要求：零丢失、可审计、不能直连生产库写。
```

他会给你的产出（要点还原）：

1. 语义压缩先行（他的数学美学：先把问题变小）：

```python
# 200 万行 → 47 个模式族（日期格式家族 + 异常编码 + null 变体）
# sentence-transformers 本地 embedding + ChromaDB 聚类，零 API 调用
# 每族抽 3-5 条代表样本 → SLM 只处理 47 次，不是 200 万次
```

2. 本地 SLM（Phi-3 via Ollama）生成修复逻辑，输出被严格约束为 lambda：

```json
{
  "transformation": "lambda x: datetime.strptime(x, '%m-%d-%Y').strftime('%Y-%m-%d')",
  "confidence_score": 0.94,
  "pattern_type": "date_format"
}
```

3. 安全门执行前的强制检查（他的 Rule 3）：不是 lambda 开头、含 `import/exec/eval/os` 一律拒绝并路由到人工隔离。
4. 执行纪律：置信度 <0.75 的族不自动修（进人工隔离面板）；修复先进 staging 沙箱、dbt 测试通过才晋级生产；混合指纹（语义相似 + 主键 SHA-256）防"John Doe"和"Jon Doe"被误并。
5. 批次收尾对账：`200 万 == 修复 199.3 万 + 隔离 0.7 万`——不满足立刻 Sev-1。

**价值**：原计划 3 个月的人工清洗，变成 4 小时的自动流水线 + 0.7 万行带完整上下文的人工复核队列；每一行变更都有审计收据可查。

## 实战案例 2：拒绝"让 GPT 直接改数据"的方案评审

背景：团队提出"把脏数据批量喂给 GPT-4，让它输出干净版本直接回写"，看起来更快。

雇佣他时可以这样提示：

```
团队方案：脏数据 50 万行导出 → GPT-4 批量清洗 → 回写。
请评估该方案的可行性。
```

他会做的事：

1. 三连否决，每条都是生产事故级别的理由（他的人设记忆里全是这类教训）：

```markdown
否决 1（PII）：数据含客户手机号，出网即违规——"Ollama only，
  提云端 API 这个话题就到此为止。"
否决 2（不可审计）：GPT 直接输出数据值，幻觉覆写无法回滚、
  无法解释——"你无法审计一个悄悄改掉客户银行账号的字符串。"
否决 3（成本与规模）：50 万次云端推理，比 12 次本地推理贵 4 个数量级。
```

2. 给出替代架构：语义聚类 + 本地 SLM 生成 lambda + 沙箱执行 + 审计日志——每一步可回滚可解释。
3. 对比交付：两条路线的安全、成本、速度三轴对比表，让决策有据。

**价值**：拦下一次"看起来高效"的方案——这类方案上线三个月后爆出数据污染时，修复成本是当初的百倍。

## 使用技巧

- 使用他之前先明确 PII 边界，他会据此锁定技术栈（本地 vs 可用云）。
- 修复目标的业务规则（日期格式、编码标准）说清楚，lambda 生成的目标才有锚。
- 人工隔离面板别当摆设：每批 <10% 的隔离率是他的健康指标，超过说明上游数据源有新问题。
- 他是修复层专科：管道设计、仓库架构请找 **Data Engineer**，他只管"数据已坏且管道不能停"的场景。
