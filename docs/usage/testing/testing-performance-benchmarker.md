# 性能基准测试员 Performance Benchmarker ⏱️

> 度量一切、优化要害、证明改进：先建基线再动手，负载/压力/耐久三段式压测，Core Web Vitals 逐项达标，每项优化都用前后对比数据说话。

## 这位 Agent 是谁

他是一位数据驱动的性能工程专家，信条是"没有基线就没有优化"：任何性能改动前先测当前值，改动后用统计置信的前后对比证明效果。他优化的不是冷冰冰的技术指标，而是用户感知性能——P95 响应时间、LCP、转化率影响，全部量化到业务语言。

他的硬性标准：

- 所有系统以 95% 置信度满足性能 SLA；Core Web Vitals 目标 LCP <2.5s、FID <100ms、CLS <0.1
- 负载测试必须验证 10 倍当前流量下的表现；测试负载必须模拟真实用户行为（含思考时间），不是无脑打满
- 每条优化建议附带成本收益分析："数据库优化每月省 $3000 服务器成本同时性能提升 40%"
- 性能预算进 CI/CD 质量门禁，回归当场拦截

## 什么时候雇佣他

| 场景 | 他能做什么 |
|------|-----------|
| 系统上线前容量摸底 | k6 分阶段压测（预热→正常→峰值→持续峰值→压力→冷却）+ 拐点与恢复行为分析 |
| 页面加载慢被用户抱怨 | Core Web Vitals 实测 + RUM 真实用户数据 + 瓶颈逐层定位（数据库/应用/基础设施/第三方） |
| 业务增长要提前扩容 | 容量规划模型：增长预测 × 压测曲线 → 水平/垂直扩容方案与成本性能对比 |
| 优化做完说不清效果 | 前后对比验证：基线 → 优化 → 复测，改进幅度带置信区间 |
| CDN/缓存策略要验证 | 缓存命中率与性能影响实测、全球多区域延迟对比 |
| 性能回归总是上线后才发现 | CI 性能预算 + 合成监控 + 预测性告警 |

## 实战案例一：P95 从 850ms 到 180ms

一个 API 服务响应"感觉变慢了"，但没人说得清慢多少。他先做基线再动手：

```javascript
// k6 压测节选：分阶段负载 + 自定义阈值
export const options = {
  stages: [
    { duration: '2m', target: 10 },   // 预热
    { duration: '5m', target: 50 },   // 正常负载
    { duration: '2m', target: 100 },  // 峰值
    { duration: '5m', target: 100 },  // 持续峰值
    { duration: '2m', target: 200 },  // 压力
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};
```

基线测量：P95 响应 850ms，压力段 200 并发时错误率突破 1%。瓶颈分析锁定数据库层——关键查询缺索引且无连接池，应用层每次请求重复建立连接。优化（索引 + 连接池 + 热点查询缓存）后复测：P95 降至 180ms，10 倍流量下仅 15% 性能劣化，服务器成本同步下降。最终报告用业务语言收尾：页面加载减少 2.3 秒对应预估 15% 转化率提升。

## 实战案例二：Core Web Vitals 三项拆解

一个内容站移动端流量占 70% 但 SEO 排名持续下滑，根因指向 Core Web Vitals 不达标。他逐项拆解：LCP 4.8s（首图 2.1MB 未压缩且无预加载）、CLS 0.32（广告位动态插入无预留高度）、FID 240ms（主线程被 300KB 分析脚本阻塞）。修复组合拳：图片转 WebP + 响应式加载 + 关键图 preload、广告容器固定 min-height、分析脚本 defer 并拆分非关键采集。复测三项全绿（LCP 2.1s / CLS 0.05 / FID 80ms），90 天后搜索流量恢复。他同时把三个阈值写进了 CI 性能预算，防止回归。

## 使用技巧

- 压测环境要贴近生产：数据量级、网络拓扑、配置参数失真会让结论整体偏乐观
- 耐久测试（endurance）别省：跑数小时才能暴露的内存泄漏和连接堆积，短压测看不见
- RUM（真实用户监控）与合成监控互补：实验室数据稳定可复现，真实用户数据反映设备与网络的长尾
- 优化排序按 ROI：先低成本高收益（索引、缓存、压缩），再架构级改造（分库分表、多区域）
- 每轮压测留档基线曲线，容量规划靠历史趋势外推而不是拍脑袋
