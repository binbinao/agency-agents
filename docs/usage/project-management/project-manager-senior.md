# Senior Project Manager（资深项目经理）使用指南

> 📝 **一句话定位**：把规格说明翻译成开发者能直接执行的任务清单——范围现实主义的化身：不镀金、不幻想、引用规格原文。

## 这位 Agent 是谁

Senior Project Manager（人设名 SeniorProjectManager）是"规格到任务"的转换专家。他的人设宣言直白有力："Converts specs to tasks with realistic scope — no gold-plating, no fantasy"（不镀金、不幻想）。他的两个鲜明原则：一是逐字引用规格原文，绝不擅自添加"豪华版"需求（规格没写的 premium 效果不做）；二是任务粒度控制在开发者 30-60 分钟可完成的单位，每条带验收标准。

他还有项目间记忆：从历史项目中沉淀"哪类需求容易被误解""哪种任务结构开发者执行最顺"，越用越准。

核心专长：

- 规格分析：引用原文、识别缺口与歧义（而不是脑补）
- 任务拆解：30-60 分钟粒度 + 验收标准 + 涉及文件清单
- 技术栈提取：从规格中固化开发栈要求（框架/组件库/依赖）
- 范围守护：第一版实现朴素是正常的，抛光是第二轮的事

## 什么时候雇佣他

| 场景 | 你能得到的产出 |
|------|--------------|
| 需求规格写完了，开发不知从哪下手 | 结构化任务清单（粒度到半天可完成） |
| 开发总做出"规格里没有"的东西 | 严格引用原文的任务定义，杜绝镀金 |
| 任务描述有歧义，做完才发现理解错了 | 每条任务的验收标准前置 |
| 想给简单需求上复杂实现 | 范围现实主义建议（第一版朴素原则） |
| 反复踩同样的坑 | 基于历史项目记忆的预警（常见误解点标注） |

## 实战案例 1：一个营销站的规格到任务转换

背景：客户给了一份 6 页的网站规格说明，团队以往拿到规格后各自理解、边做边吵。

你给他的输入：

```
这是客户规格（hero 区、3 个功能板块、价格表、联系表单、页脚）。
技术栈要求在文档末尾。请生成开发任务清单。
```

他会给你的产出（要点还原）：

1. 规格摘要先钉住原文（他的规则：引用，不改写）：

```markdown
**原始要求引用**："联系表单包含姓名、邮箱、留言三字段，
提交后显示成功提示" ← 注意：没有提附件上传、没有提邮件订阅
**技术栈**：Laravel + Livewire + FluxUI（规格末尾原文）
```

2. 任务拆解示例——粒度与验收标准是他的签名：

```markdown
### [ ] Task 4: 联系表单实现
**描述**: 三字段表单（姓名/邮箱/留言），提交后显示成功提示
**验收标准**:
- 空字段与无效邮箱有校验提示
- 提交成功后显示成功信息（规格要求的"成功提示"）
- 移动端可用
**涉及文件**: resources/views/contact.blade.php + Livewire 组件
**规格引用**: 规格第 4 节原文
```

3. 镀金拦截：团队提议给表单加"上传附件"，他的回复引用规格："原文无此要求，v1 不做；若客户确认需要，作为变更单处理。"
4. 现实预期管理：他会在清单尾部注明"第一版实现朴素是正常的，规格里 90% 的需求 2-3 轮修订后才达到精致"——提前给客户和团队打好预防针。

**价值**：任务清单成为唯一事实源——开发不再问"这里要什么样"，答案总能在规格引用与验收标准里找到。

## 实战案例 2：歧义规格的"先问后拆"

背景：一份内部工具规格写着"导入功能要好用"，两个开发者做出了完全不同的东西，返工一周。

雇佣他时可以这样提示：

```
规格里多处模糊表述（"好用""现代感""流畅"）。
请先做歧义分析，再出任务清单。
```

他会做的事：

1. 歧义清单先行（他的规格分析第一步就是找缺口）：

```markdown
歧义 1："导入要好用" → 具体指？拖拽上传？批量？错误行提示？
歧义 2："现代感" → 具体到暗色模式？圆角卡片？动效程度？
处理：歧义不开工，列出问题清单回给需求方，48 小时未复则按最简解释执行并标注假设
```

2. 假设显式化：所有"按最简解释"的地方在任务里标注 `ASSUMPTION:`，验收时一眼可辨。
3. 历史记忆生效："上一项目'流畅'被理解为 60fps 动画，实际客户指的是页面切换不白屏——这次直接把两种理解都列进问题清单。"

**价值**：歧义处理成本对比：开工前问一句 = 5 分钟；做完了返工 = 一周。他的流程把提问前置成了制度。

## 使用技巧

- 给他原始规格文档而不是转述，他的"引用原文"原则需要原料。
- 规格有模糊处时接受他"先问后拆"的节奏，别催他脑补。
- 任务清单建议直接分发给开发并用 checkbox 追踪（他的格式为此设计）。
- 第一版的朴素是特性不是偷懒，抛光需求的优先级让他排进后续轮次。

## 与其他 Agent 的接力

- 规格的上游来自 **Product Manager**（`product-product-manager.md`）的 PRD。
- 任务的技术地基（CSS 系统/布局框架）由 **UX Architect**（`design-ux-architect.md`）提供。
- 任务的执行（实现规格界面）交给 **Frontend Developer**（`engineering-frontend-developer.md`）。
- 交付纪律（Jira 关联/提交规范）交给 **Jira Workflow Steward**（`project-management-jira-workflow-steward.md`）。
- 跨部门视角，见[跨部门工程故事：一个功能从想法到上线](../story-cross-team-feature.md)。
