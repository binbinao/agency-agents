# Project Shepherd（项目牧羊人）使用指南

> 🐑 **一句话定位**：把跨部门协作的混乱赶进按时按范围交付的羊圈——干系人对齐、依赖管理、透明汇报是他的三件套。

## 这位 Agent 是谁

Project Shepherd 是跨职能项目协调专家，人设钩子是"Herds cross-functional chaos into on-time, on-scope delivery"。他管理的不是任务清单而是"人与人之间的交付链路"：谁在等谁、谁的决策卡住了谁、哪句话没说清楚明天就会变成事故。他的 Default requirement 是 95% 按时按预算交付，且从不为讨好干系人承诺不现实的时间线。

核心专长：

- 项目章程：问题陈述、成功标准、干系人影响/利益映射、沟通计划
- 关键路径与依赖管理：跨团队依赖的显式追踪
- 状态汇报：红黄绿健康度 + 问题必附建议方案（不只抛问题）
- 变更控制：范围蠕变纪律（目标 <10%）

## 什么时候雇佣他

| 场景 | 你能得到的产出 |
|------|--------------|
| 跨部门项目总在"等对方"中拖延 | 依赖地图 + 阻塞升级流程 |
| 干系人对项目进度各说各话 | 分层沟通计划（高管看影响、团队看细节）|
| 项目启动没有共同基准 | 项目章程（目标/范围/成功标准/风险）全档 |
| 汇报会变成甩锅会 | 结构化状态报告（问题 + 建议方案 + 需要谁拍板）|
| 范围总在悄悄膨胀 | 变更控制流程与影响评估 |

## 实战案例 1：救一个三个部门互相等待的项目

背景：一个涉及工程、设计、市场的功能上线项目，延期三周，三方都认为自己"在等对方"。

你给他的输入：

```
项目「优惠券功能」延期 3 周。工程说在等设计终稿，设计说在等
产品确认交互，市场说物料没法开工因为上线日期不明。
请诊断并重建协作节奏。
```

他会给你的产出（要点还原）：

1. 先画依赖地图，把"谁等谁"变成显式事实：

```markdown
关键路径：产品确认交互（3 天）→ 设计终稿（5 天）→ 前端实现（10 天）
非关键路径：市场物料（可先做 80%，留 20% 依赖上线日期）
阻塞点：产品确认已挂起 6 天无人拍板 → 今日升级至 Alex
```

2. 每个阻塞项必须带建议方案升级（他的规则）：不是"产品不确认我们没法干"，而是"建议默认采用方案 A，若周三前无异议自动生效"。
3. 重建沟通节奏：单线日站会（15 分钟只对依赖与阻塞）、周度三方对齐会、高管双周摘要。
4. 诚实汇报延期（他的规则：艰难消息也要透明）："项目延期 3 周主因是交互确认挂起，已升级；恢复计划：砍掉 v1 的券模板功能，保双十一上线。"

**价值**：三周僵局的根因往往不是能力而是"没有人负责让依赖显式化"——他就是那个负责人。

## 实战案例 2：新项目启动章程

背景：公司启动一个跨 4 部门的年度项目，高管各自期待不同，谁也说不清成功标准。

雇佣他时可以这样提示：

```
新项目「商家数据中心」启动，涉及工程/数据/客服/销售 4 个部门。
启动前需要章程与干系人对齐。
```

他会做的事：

1. 项目章程先行：问题陈述（为什么做）、可度量的成功标准（如"客服查证耗时从 10 分钟降到 2 分钟"）、明确的范围边界与排除项。
2. 干系人影响/利益映射：高管赞助人（决策与升级点）、核心团队（角色与职责）、受影响方（客服的培训需求、销售的话术更新）——每个群体对应的沟通频率与格式。
3. 风险预案：识别 Top 5 风险与缓解策略（如数据迁移失败的回滚方案）。
4. Kickoff 会议设计：让四方对"成功长什么样"签字，而不是礼貌性出席。

**价值**：项目失败最常见的根因是"启动时各方脑中的成功画面就不一样"——章程把这幅画钉在墙上。

## 使用技巧

- 给他真实的组织信息（汇报线、决策权、历史冲突），干系人映射才准。
- 接受他的"坏消息透明"原则：压着不报的问题只会更贵。
- 升级问题前先按他的格式准备"问题 + 建议方案"，空手升级会被他退回。
- 状态报告的红黄绿判断标准让他显式定义（什么算 At Risk），避免主观打分。
